## Context

平台后端主体数据（paper trading、backtest、golden pit、fund_flow_cache 等）已迁移到 PostgreSQL（`DATABASE_URL`，生产指向 `81.70.44.68:5432/marcus_trading`），但核心主数据仍分散在本地 SQLite：`data/stock_pool.db`（5 张表：`stock_pool` 5,547 行、`sectors` 1,097、`concept_sectors` 71、`stock_concept_map` 105,611、`stock_sector_map` 0）、`data/cache.db` 的 `etf_pool`（1,397 行），以及 `data/trades.db` 中仍被 `jobs/pre_market_scan.py` 活跃读写的 `sector_config`（7 行）。8+ 个后端 API/服务与 4+ 个 jobs 各自 `sqlite3.connect` 打开同一文件。`news.db`（36,544 行）按用户决策本次不迁移，继续留在 SQLite。`watchlist` 表（132 行）已无任何代码引用，直接删除。

## Goals / Non-Goals

**Goals:**
- `stock_pool.db` 全部 5 张表、`etf_pool` 表、`sector_config` 表迁移到 PostgreSQL，提供一次性数据迁移脚本。
- 所有读写方（API、服务、jobs、core 引擎）切换到 PG，消除针对这些数据集的 `sqlite3.connect`。
- 删除遗留 `watchlist` 表（不迁移数据）。
- `backend/app/api/db.py` 通用查询接口对已迁移数据集走 PG，`news` 保留 SQLite 只读通道。
- 保留现有 API 请求/响应契约（`/db/query`、`/db/schema` 的 `{rows, columns}` 结构）。

**Non-Goals:**
- `news.db` 数据迁移（明确不做，仅必要代码适配）。
- `data/trades.db` 其余 SQLite 副本（orders/trades/positions/account_info/daily_snapshot 等，PG 已有 `paper_*` 等价物）的清理——仅作为备份保留，不在本变更删除。
- `cache.db` 其余表（`stock_quotes`、`cube_data`、`etf_detail` 等）迁移。
- `data/backtest/*/paper/trades.db` 等回测产物与 `apps/paper-trading/data/*` 旧副本的清理（不属本变更范围）。

## Decisions

### D1: 新增 ORM 模型到 `backend/app/models/market_orm.py`
在现有 `market_orm.py`（已有 `MarketDiagnosis`）中新增 7 个模型：`StockPool`、`Sector`、`ConceptSector`、`StockConceptMap`、`StockSectorMap`、`EtfPool`、`SectorConfig`，并在 `backend/app/database.py` 的 `init_db()` 中 import 注册。
- **理由**：模型与主数据同属 market 域；沿用既有 `Base.metadata.create_all` 建表机制，无需单独 DDL。
- **备选**：新建 `market_reference.py` —— 亦可，但会多一个 import 点；同文件更符合现有 `market_orm.py` 命名。

### D2: 后端读方收敛到共享仓储模块 `backend/app/services/market_reference.py`
新增只读仓储：`get_stock_name(symbol)`、`get_stock_industry(symbol)`、`search_stocks(q)`、`get_concept_stocks(...)`、`get_etf_pool(...)`、`get_sector_config(...)`，内部使用 `SessionLocal` + SQLAlchemy。
- **理由**：10+ 个调用点目前各写一段 `sqlite3.connect`，收敛后避免重复样板，且便于后续加缓存/索引。
- **备选**：逐文件直接改 SQLAlchemy —— 改动点分散、易漏，不采用。

### D3: core/jobs 侧用 psycopg2 直连（沿用 paper_engine 模式）
`core/stock_pool_manager.py`（写入）、`core/xueqiu_engine.py`（ETF 池读写）、`jobs/pre_market_scan.py` 的 `SectorConfigManager`（sector_config 读写）用 `psycopg2` + `DATABASE_URL` 环境变量直连，`INSERT ... ON CONFLICT ... DO UPDATE`（批量用 `executemany`）。
- **理由**：`apps/paper-trading/paper_engine.py` 已是此模式；core/jobs 独立于 backend venv 运行，直连 psycopg2 依赖最少。
- **备选**：让 core/jobs 引入 SQLAlchemy —— 需要后端环境，增加耦合，不采用。

### D4: 列类型映射
| SQLite | PostgreSQL |
| --- | --- |
| TEXT PK | VARCHAR / TEXT PRIMARY KEY |
| INTEGER / INTEGER PK AUTOINCREMENT | INTEGER / GENERATED BY DEFAULT AS IDENTITY（迁移时显式插入 id） |
| REAL | DOUBLE PRECISION |
| TEXT (JSON 字段，如 `sector_config.indices/etfs/stocks/etf_codes`、`etf_pool.data`) | JSONB（ORM 用 `JSONB` 类型，代码侧保持 dict 读写） |

索引照搬：`stock_pool(industry)`、`stock_pool(market)`、`stock_pool(is_st)`、`stock_sector_map(sector_name)`、`concept_sectors(concept_name)`、`stock_concept_map(concept_name)`。

### D5: 迁移脚本 `scripts/migrate_market_data_to_pgsql.py`
照 `scripts/migrate_sqlite_to_pgsql.py` 模式：`--dry-run` 只统计；正式运行先 `DELETE`/`TRUNCATE` 目标表再全量 `INSERT`；完成后输出各表行数；不删除 SQLite 源文件。覆盖 `stock_pool.db` 5 表、`cache.db` 的 `etf_pool`、`trades.db` 的 `sector_config`；并在迁移末尾对 `data/trades.db` 执行 `DROP TABLE IF EXISTS watchlist`。
- **部署顺序**：先跑脚本（数据入 PG + watchlist 删除），再发代码（读方切 PG）。旧 SQLite 文件保留作备份与回滚源。

### D6: db.py 双后端路由
`open_db()` 改为按 `db` 名路由：
- `stock_pool` → PG（查询 `stock_pool` 等 5 表）；`etf_pool` → PG（`etf_pool` 表）。
- `news`（及未迁移的 `trades`、`cache` 其余表）→ 保留 SQLite 只读。
- `POST /db/write` 对 PG-backed 数据集拒绝（HTTP 400），仅允许对遗留 SQLite 数据集写入，避免对生产 PG 的任意 SQL 写。
- 参数化查询防注入（`where`/`table` 白名单或 `%s` 占位符），保持响应结构 `{rows, columns}` 不变。
- **理由**：`news` 不迁移 → 必须保留 SQLite 通道；写接口对共享 PG 开放任意 SQL 风险高。

### D7: 高频读缓存
`get_stock_name` 等热路径保留/复用现有内存缓存（`portfolio._stock_name_cache` 思路），迁移后加 TTL 缓存，减少远端 PG 往返。
- **理由**：PG 在远端（`81.70.44.68`），名称/行业查表是毫秒级热点，不能每次请求都开连接。

### D8: SectorConfigManager 改造
`jobs/pre_market_scan.py` 的 `SectorConfigManager` 改为读写 PG `sector_config` 表：`_load_or_seed()` 改为 PG 查询 + 空表 seed，`update_stocks()` 改为 PG `UPDATE`，`sync_from_etf()` 逻辑不变仅落库通道切换；模块级内存缓存 `_cache` 保留。
- **理由**：类已有内存缓存兜底，改动集中在 `_conn/_load_or_seed/update_stocks` 三处，行为可保持完全一致。
- JSON 列用 JSONB 存储，代码侧仍 `json.loads`/dict 操作（或直接让 psycopg2 处理 dict）。

### D9: watchlist 删除
迁移脚本末尾 `DROP TABLE IF EXISTS watchlist`（`data/trades.db`），不迁移数据；经核查无任何代码引用该表（`dynamic_watchlist.py` 是独立的 JSON 文件功能，不受影响）。
- **理由**：132 行遗留数据无读写方，保留无意义；删除前打印行数便于审计。

## Risks / Trade-offs

- [远端 PG 延迟] → 共享仓储内做短 TTL 内存缓存；连接池复用 `SessionLocal`（已有 `pool_pre_ping`）；避免 N+1 查询。
- [概念映射 10 万+ 行全量刷新] → 写方用 `executemany` + `ON CONFLICT`；刷新任务可分批 commit，避免长事务。
- [news.db 留在本地] → `db.py` 的 `news` 通道明确 SQLite；文档注明 news 数据仅存在于运行该文件的节点。
- [`/db/write` 行为收紧] → 属于 BREAKING（对 PG-backed 数据集拒绝写），在 proposal 已标注；agent/前端工具主要用 query/schema，影响可控。
- [watchlist DROP 不可逆] → SQLite 文件整体保留为备份；脚本删除前打印行数，可随时从备份恢复。
- [sector_config JSON 列类型] → 从 TEXT+`json.dumps` 改为 JSONB 后，若外部脚本以字符串拼接 SQL 写入会不兼容；已同步改造两个 seed 脚本。
- [回滚] → 迁移脚本幂等可重跑；旧 SQLite 文件保留，必要时改回读方即可恢复。

## Migration Plan

1. 先合入模型 + 迁移脚本，本地/生产执行 `python scripts/migrate_market_data_to_pgsql.py --dry-run` 核对行数（stock_pool 5 表、etf_pool、sector_config、watchlist 行数）。
2. 正式执行迁移（清空目标表 → 全量写入 → DROP watchlist → 校验行数一致）。
3. 合入读方/写方改造代码并部署；验证 `/api/v1/market/search`、`/api/v1/etf`、行业板块、`/db/query`、盘前扫描的板块配置加载。
4. 观察一个股票池刷新周期（`jobs/stock_pool_manager.py`）与一次盘前扫描，确认写 PG 正常。
5. 回滚方案：读方代码回退到 SQLite 版本即可（数据未删除，watchlist 可从备份恢复）。
