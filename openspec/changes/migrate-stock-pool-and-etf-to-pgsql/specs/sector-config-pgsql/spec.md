## ADDED Requirements

### Requirement: Sector config persisted in PostgreSQL
The system SHALL persist the sector linkage configuration (`sector_config`, currently in the SQLite `data/trades.db`) in PostgreSQL.

#### Scenario: Tables created idempotently in PostgreSQL
- **WHEN** the migration script or backend initialization runs
- **THEN** the `sector_config` table SHALL exist in PostgreSQL with `sector_key` as primary key and the same columns as the SQLite source

#### Scenario: All sector config rows migrated
- **WHEN** the migration script completes without `--dry-run`
- **THEN** every row from the SQLite `sector_config` table SHALL exist in the PostgreSQL `sector_config` table

### Requirement: SectorConfigManager reads and writes PostgreSQL
The system SHALL update `SectorConfigManager` in `jobs/pre_market_scan.py` to read, seed, and update `sector_config` through PostgreSQL instead of `sqlite3.connect` to `data/trades.db`.

#### Scenario: Load seeds from PostgreSQL
- **WHEN** `SectorConfigManager` is first initialized and the `sector_config` table is empty
- **THEN** it SHALL seed the default sector linkage rows into the PostgreSQL `sector_config` table

#### Scenario: Dynamic stock update writes to PostgreSQL
- **WHEN** `SectorConfigManager.update_stocks()` is called
- **THEN** the `stocks` column SHALL be updated in the PostgreSQL `sector_config` table

### Requirement: Seed scripts target PostgreSQL
The system SHALL adapt the `sector_config` synchronization SQL generated by `scripts/seed_golden_pit_etf_config.py` and `backend/scripts/seed_golden_pit_etf_config.py` to PostgreSQL syntax.

#### Scenario: Seed output is PostgreSQL-compatible
- **WHEN** the seed script runs
- **THEN** the generated INSERT statements SHALL target the PostgreSQL `sector_config` table and use PG-compatible syntax

### Requirement: Legacy watchlist table removed
The system SHALL drop the `watchlist` table from the SQLite `data/trades.db`; no code SHALL read or write the watchlist table.

#### Scenario: Watchlist dropped during migration
- **WHEN** the migration script runs
- **THEN** the `watchlist` table SHALL be dropped from the SQLite `data/trades.db` and its data SHALL NOT be migrated

#### Scenario: No runtime references remain
- **WHEN** the migration completes
- **THEN** no backend, job, or core module SHALL reference the `watchlist` table (the JSON-based `dynamic_watchlist` feature is unaffected)
