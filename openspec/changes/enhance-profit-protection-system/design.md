## Context

当前 `StopLossMonitor` 的止损体系（规则 0a→0b→1→2→2.5→2.6→3）全部是"价格已跌后"的被动防守。7/14-7/24 亏损复盘发现两个独立漏洞：

1. **Iron Rule 2 保护真空区**：保护层级用"当前浮盈"判定，导致股价暴跌时保护线同步下滑、永远追不上。拓维信息从 +12% 一日暴跌至 +2%，31 秒轮询周期内保护线从 +5% 一路滑到 None，全程未触发。
2. **缺少主动止盈**：三笔亏损股的 KDJ_K 在暴跌前 3-5 天均已进入超买区（紫光 90、光线 81、拓维 83），但系统无任何超买止盈逻辑。现有规则 2.5（技术背离）仅检查 KDJ J > 100 且要求 ≥3 个信号同时触发，门槛过高。

两个漏洞的修复互补且不冲突：真空区修复管"跌了之后要拦住"，超买止盈管"涨太多了要提前收网"。

## Goals / Non-Goals

**Goals:**
- P1: Iron Rule 2 保护层级判定改用会话最高浮盈（`_session_max_float`），当日峰值一旦到达某层级，保护线当天不再下移
- P2: 新增规则 2.3 超买止盈，KDJ_K ≥ 80 触发三级递进减仓（30%/50%/100%）
- P2 数据获取复用 `_tech_divergence.py` 现有链路，新增 `get_overbought_indicators()` 暴露原始 KDJ_K / RSI6
- 改动集中在 `stop_loss_monitor.py` 和 `_tech_divergence.py` 两个文件

**Non-Goals:**
- 不改动规则 0a、0b、1、2.5、2.6、3 的行为
- 不引入 MACD 顶背离作为超买止盈的额外条件（MACD 已在规则 2.5 中覆盖）
- 不修改 API 接口或数据库 schema
- 不在 `enhance-stop-loss-dynamic-adjustment` change 的基础上重复改动（两个 change 修改不同规则，无冲突）

## Decisions

### Decision 1: P1 — 会话级峰值追踪（方案 A）

**选择**：新增 `_session_max_float: Dict[str, float]` 字典，每个轮询周期更新当日最高浮盈，用于替代当前浮盈判定保护层级。在 `_daily_reset()` 中清零。

```
轮询周期    当前浮盈    会话峰值    判定层级    保护线     触发？
──────────────────────────────────────────────────
09:45       +12%       +12%        T3         +5%       ✗ (12 > 5)
10:30        +8%       +12%        T3         +5%       ✗ (8 > 5)
11:15        +5%       +12%        T3         +5%       ✓ (5 ≤ 5) → 触发!
```

与当前行为的关键区别：
| 场景 | 当前（当前浮盈判定） | 修复后（峰值判定） |
|:---|:---|:---|
| +12%→+5% 一日暴跌 | 保护线 +5%→None，不触发 | 保护线固定 +5%，触发 |
| +12%→+6% 一日微跌 | 保护线 +5%→+1.5%，不触发 | 保护线固定 +5%，不触发 |
| 上午+3%→下午-1% | 保护线 0%→None，不触发 | 保护线固定 0%，触发保本 |

**备选方案**：
- **方案 B（快跌检测器）**：只检测单周期跌幅 > 振幅×2。改动最小但只覆盖极端暴跌，慢跌两天仍然漏。已否决。
- **方案 C（双轨保护）**：峰值层级永久激活直到清仓。过于激进——如果股票三周前到过 +15%，三周后跌到 +5% 还要按 T3 保护线强制卖出不合理。已否决。

**会话级别的理由**：每日重置意味着"今天的峰值保护今天用"。如果股票昨天 +12% 今天 +3%，今天用今天的峰值 +3% 判定 → T1 保护（保本），不会用昨天的 +12% 去强制 +5% 卖出。这平衡了保护力度和持仓稳定性。

### Decision 2: P2 — 三档递进超买止盈

**选择**：按严重程度递进的三个触发条件，档位越高卖出比例越大。

| 档位 | 条件 | 卖出比例 | 优先级 |
|:---|:---|:---:|:---:|
| 第三档 | KDJ_K ≥ 80 连续 3 个交易日 | 100% | 最高 |
| 第二档 | KDJ_K ≥ 80 + RSI6 ≥ 75 + 单日涨幅 > 3% | 50% | 中 |
| 第一档 | KDJ_K ≥ 80（首次触发） | 30% | 最低 |

同一轮询周期内按优先级判定，高优先级命中后不再检查低优先级。

**连续交易日判定**：`_overbought_history[symbol]` 存储 KDJ_K ≥ 80 的日期列表。当日日期与列表中最新日期比较：连续自然日（允许间隔 1-2 天，因周末/节假日）→ 累加；间隔 > 3 天 → 重置计数。

**备选方案**：
- **KDJ J > 100 单一阈值**：更极端但更晚触发。紫光 7/6 KDJ_K=80 时 J 可能还没到 100，会错过 3 天预警窗口。已否决。
- **MACD 死叉联动**：等 MACD 死叉确认再减仓太晚，违背"主动止盈"的定位。已否决。

### Decision 3: P2 — 规则 2.3 插入位置

**选择**：优先级链 `0a→0b→1→2→2.3→2.5→2.6→3`，超买止盈位于铁律二（规则 2）之后、技术背离（规则 2.5）之前。

**理由**：
- 铁律二保护"价格已经在跌"的利润 → 优先级更高（紧急）
- 超买止盈是"价格可能即将跌"的预判 → 优先级次之（预防）
- 两者都命中时（价格已从高点跌 + 仍在超买区），铁律二先拦截
- 超买止盈可在价格还在高位时从容减仓，与铁律二的"追着跌的卖"形成互补

### Decision 4: P2 — 数据获取复用现有链路

**选择**：在 `_tech_divergence.py` 中新增 `get_overbought_indicators(symbol, cache)` 函数，返回 `(kdj_k, rsi6, daily_change_pct)` 三元组。60 秒缓存独立于 5 信号评估的 1 小时缓存。

数据来源（优先级）：
1. 腾讯 qt.gtimg.cn 实时行情（获取 current_price, change_pct）
2. Tushare stk_factor_pro 昨日盘后确认值（获取 KDJ_K, RSI6）
3. `core.realtime_indicators.calculate_realtime_indicators()` 盘中估算（获取今日 KDJ/RSI 估算值）

KDJ_K 取值逻辑：优先用盘中实时估算值（`realtime.kdj_k`），降级时用昨日盘后确认值（`df_tech['kdj_k_qfq']`）。盘中估算值来自腾讯实时价 + Tushare 历史计算的混合算法。

## Risks / Trade-offs

- **[Risk] P1 会话峰值可能导致正常日内波动触发误卖** → 早盘冷静期（09:30-09:45）已阻止执行，且峰值通常需要价格先到达后才能判定。如果开盘冲高 +12% 然后回落到 +5%，这是 7% 的日内回撤，触发是合理的。如果后续发现误触发过多，可引入"峰值需维持 ≥2 个轮询周期"的确认机制
- **[Risk] P2 超买止盈可能过早减仓** — KDJ_K ≥ 80 在强势上涨行情中可能持续数日，减仓 30% 后会错过后续涨幅 → 这是主动止盈的本质权衡：用部分潜在收益换取确定性。30% 首次减仓是温和的，留 70% 继续跟随趋势。如果后续回测证明 30% 太激进，可调为 20%
- **[Risk] P2 连续交易日判定在长假后可能误判** → 使用自然日间隔 ≤ 3 天的规则：如果上次 KDJ ≥ 80 是 5 天前（中间有周末），间隔仍有 2 个交易日，计数继续。如果 > 3 天（如国庆长假），计数重置
- **[Trade-off] P2 数据获取引入额外 HTTP 调用增加延迟** → 复用 `_tech_divergence.py` 的缓存机制（60 秒 TTL），同一股票在 60 秒内不重复请求。且 Tushare stk_factor_pro 查询与规则 2.5 共享底层数据
